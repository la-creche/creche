# creche-release: one home for the host's release process

> Status as of 2026-11-14: Done. The host release component is live (2026-11-03). The recommendation and the options below are the record of the decision.
> Host names, addresses and accounts are placeholders. The operator's private notes hold the real values.

Date: 2026-10-31. Status: decided 2026-10-31 (§8). The operator chose Option 1,
stage 1 now, and a separate root step for the site file. Stage 1 PR 1
merged: la-creche/private-docs#42. It keeps stage7 §2.3's rule that a request
carries no hash: root reads the registry commit itself, and the follower only
decides when to file. §6.1 lists what can leave `private-docs`.

## 0. Recommendation

Build **Option 1**: a small `creche-release` repository that declares what
The host runs beside the components. It ships as one new component, `host`.
Its merges mint `host-vX.Y.Z` tags, and each tag reaches the host through the
follower and one tap, exactly as `chaperone` or `mcp-servers` does today.

Build it in three stages. Each stage works alone, and each one can stop the
plan without leaving the host half-moved.

1. **Stage 1, no new repo.** The follower watches the registry's `mcp/` tree
   and files a tapped `redeploy` of `mcp-servers` (`mcp-registry-follow-design.md`
   §6). This closes the `headroom` class of gap. About 4 PRs.
2. **Stage 2, the new repo.** `creche-release` holds the host units that
   belong to no component, the scripts they run, and `host.toml`, the follow
   policy. Handover installs them with a tap. About 8 PRs and one host window.
3. **Stage 3, retire the hand deploy.** The units point at
   `/opt/components/host`. The `NOPASSWD` sudoers entry for `creche-deploy`
   goes. About 3 PRs and one host window.

What does not change: handover stays the only engine. The tap stays the only
approval. Component units stay with their components. The registry's family
files still apply with no tap (contract 06 §6).

## 1. What runs today

### 1.1 Components and tags

Every repository but `private-docs` now mints tags on merge with creche's
allocator (`handover/bin/allocate-tags.sh`).

| Component | Repo | Newest tag (2026-10-31) | Reaches the host by |
|---|---|---|---|
| `attendance`, `caregiver`, `noticeboard`, `playpen`, `handover` | creche | per component | follower, then a tap |
| `chaperone` | chaperone | `chaperone-v0.5.2` | follower, then a tap |
| `mcp-servers` | mcp | `mcp-servers-v0.1.12` | follower, then a tap |
| `registry-data` | registry | `registry-data-v0.1.1` | the sync timer, **no tap** (`Releases.NO`) |

The catalog is code: `handover/src/handover/catalog.py`. Adding a component
or a repository is a contract 06 change first.

### 1.2 The release path

1. A merge to `main` mints `<component>-vX.Y.Z`.
2. `creche-follow.timer` (<user>, every 2 minutes) runs `handover follow` and
   writes one request into `/var/lib/creche-handover/releases/requests/`.
3. `creche-handover.path` (root) starts the executor. It resolves from the
   host's own clones under `/srv/agents/code/`, checks provenance P1 to P6,
   and asks the operator's phone. The tap binds root's `manifest_sha256`.
4. The executor installs the tree, refreshes the component's unit file in
   place, restarts the unit, runs the verify hook, and keeps `.prev`.

## 2. The gaps

1. **A registry `mcp/` change waits for an unrelated mcp merge.** `headroom`
   is the case now: registry#51 merged at 12:47, the newest
   `mcp-servers` tag is from 10:33, and `/opt/mcp/headroom` does not exist.
   The caregiver already files `mcp-servers@latest` for a declared server
   that is not installed (stage7 §4.1 step 3). Root answers "nothing would
   deploy", because `latest` equals the live version.
2. **The tap does not bind the server files.** An `mcp-servers` release reads
   the registry clone's working tree at whatever commit the sync left.
3. **Host units are installed by hand,** by three different installers, and
   one drop-in has no source at all.
4. **`/opt/creche` moves with no tap.** `sudo -l` on the host shows
   `(root) NOPASSWD: /usr/local/sbin/creche-deploy`. Any process of `<user>`
   can run it, and it runs code from a tree `<user>` writes. Consolidation
   decisions §3.5 already names this finding.
5. **Registry family data applies with no tap.** This is deliberate
   (contract 06 §6, stage7 §5.3). No option below changes it.

## 3. GitOps, and what the host already has

GitOps asks for four things. The host already has three.

| Principle | Today |
|---|---|
| Desired state is declared in git | **Partly.** Component versions are tags. The host's own units, scripts and follow rules are not declared anywhere one reader can see |
| Versions are immutable | Yes: tags, signed archives for binaries, `.release-version` stamps |
| The host pulls, nothing pushes | Yes: the follower polls. CI files nothing (stage7 §3.3) |
| A reconciler converges and reports drift | Yes for components (the executor). No for host units, `/opt/creche` and the registry's `mcp/` tree |

So the missing piece is not an engine. It is a declared, released home for
The host-level parts, plus a follower that also watches the registry.

## 4. Options

### Option 1 (recommended): `creche-release` as the `host` component

A new repository, `la-creche/creche-release`.

```
creche-release/
  component.toml      the `host` manifest (contract 06 §8)
  host.toml           the follow policy (below)
  units/user/         the 12 host unit files of §1.3
  units/system/       creche-chaperone.service.d/creche.conf
  bin/                creche-watchdog.sh, creche-registry-sync.sh,
                      sync-code-corpus.sh, sbx-drift-check.sh, fleet-up
```

`host.toml` says what the follower does:

```toml
[follow]
# "newest" follows each new tag. A version string holds the component there.
chaperone = "newest"
attendance = "newest"
caregiver = "newest"
noticeboard = "newest"
playpen = "newest"
handover = "newest"
mcp-servers = "newest"
host = "newest"

[registry]
mcp = "follow"   # a change to registry mcp/ files a tapped redeploy (stage 1)
```

How it works:

1. A merge to `creche-release` mints `host-vX.Y.Z`.
2. The follower files it like any tag. The operator taps.
3. The executor installs `/opt/components/host`, installs or refreshes each
   unit under `units/`, runs `daemon-reload`, and restarts the changed
   timers.
4. The follower reads `host.toml` from `/opt/components/host`, the **live
   tree**, never from the clone. So a policy change also waits for a tap.

What stays where it is:

- Component units (`creche-attendance.service` and the rest) stay with their
  component. Contract 06 §1 rule 8 binds a unit to its tree, and step 9
  already refreshes it from the live tree.
- `creche-handover.{path,service}` and the root wrappers stay hand-installed
  (contract 06 §1.1).
- `ai-stack.service` and the personal units stay in `private-docs`, the site.

Why a new repository and not a folder in creche: creche is the product, and
the reframe makes it a layer other hosts can run. The host's timers, cadences
and drop-ins are this host's deployment. A second host gets its own
`creche-release`, or a second `host.toml`.

Cost: stage 1 about 4 PRs, stage 2 about 8 PRs, stage 3 about 3 PRs. Two host
windows. About 3 to 4 days of work in all.

### Option 2: a `host` folder inside creche, no new repository

The same `host` component, at `creche/host/`, as consolidation decisions §3.5
option 1 proposes. Stage 1 is the same.

- Better: no new repository, no new clone, no new token grant. The allocator,
  the gate and the corpus clone exist already.
- Worse: The host's units and cadences stay in the product repository. The
  chaperone drop-in has no natural home there.

Cost: stage 1 about 4 PRs, then about 7 PRs and one host window. About 2 to 3
days.

### Option 3: a full lock file, every version pinned

`creche-release/the host.lock` pins every component tag and the registry
commit. A scheduled workflow in `creche-release` opens a "bump" pull request
for each new tag. Each merge mints `the host-vN`. The follower follows only
that tag, and the executor converges the whole host to it in one tap.

- Better: the textbook GitOps shape. One file says everything the host runs.
  A pin to an older version reads as a rollback.
- Worse: **every release needs one more merge** (code merge, bump merge,
  tap). Handover refuses `kind: rollback` and a lower version today, so a
  rollback by pin needs executor work. The bump workflow needs a read token:
  `mcp` and `registry` are private on GitHub.

Cost: about 20 to 25 PRs and two host windows. About 6 to 8 days.

## 5. The design questions

### 5.1 Who deploys the deployer

The same answer as today. The executor is `handover`, a component. Its root
wrapper, its path unit and its first tree are installed by hand
(`private-docs/bin/rework-release-visit.sh`). Contract 06 §1.1: "The thing
that deploys code is not deployed by code." `creche-release` never holds
those three. A first `host` release is filed by hand
(`handover request host --wait`), because the follower never follows a first
release (stage7 §3.3 rule 1).

### 5.2 Overlap with handover

None in code. `creche-release` holds no engine, only declarations, units and
scripts. Handover gains four things:

1. a `host` row in the catalog, and a fifth `Repo` value.
2. unit install for the `host` component. Today a release only refreshes a
   unit that exists.
3. the follower reads its list and holds from the live `host.toml`, not
   from the argv of `creche-follow.service`.
4. stage 1's `redeploy` kind.

### 5.3 Does a merge to `creche-release` need a tap

Yes, always. A merge mints a tag and changes nothing on the host. Every file
in the repository reaches the host only through a `host` release, so through
a tap. That includes `host.toml`: the follower reads the installed copy.

### 5.4 New powers, said plainly

- A tapped `host` release can **add** a user timer that runs a command as
  `<user>`, and a system drop-in. Today a release may only refresh a unit that
  exists. This is the main new power, and the tap is its gate.
- The `creche` family can open PRs in `creche-release` if the operator adds it to
  `github_token_platform`. It still cannot merge (D5.1).

### 5.5 What gets smaller

- One installer for host units instead of three.
- The `NOPASSWD` sudoers entry goes (stage 3).
- `creche/systemd/` keeps only component units and the handover pair.

## 8. Decisions for the operator

1. **Which option?** Recommended: Option 1, in three stages.
2. **Start stage 1 now?** It needs no new repository, and it is the same
   under all three options. Recommended: yes.
3. **The site file.** `/etc/creche/site.env` links into `/opt/private-docs`,
   which only `creche-deploy` updates. Stage 3 needs a new way: move the site
   checkout into the `host` release, or keep a separate root step for it.
   Recommended: a separate root step for now, decided before stage 3.
4. **Visibility of `creche-release`.** Recommended: private, so the
   bootstrap scripts can move with their LAN addresses (§6.1).

5. **Can the `creche` family open PRs in `creche-release`?** It now holds
   the fences and the recipients file. A: yes. Every change still needs
   the operator's merge and a tap, which is a higher bar than `site.env` has today
   (`sudo creche-deploy`, no tap). Then the site ships in the `host` release,
   and decision 3 becomes "with the tap". B: no agent token reaches it, as
   for `private-docs` today. Agents then cannot propose unit changes, and
   decision 3 stands. Recommended: A.

The operator's answers, 2026-10-31: 1 Option 1. 2 yes, start now. 3 a separate
root step. 4 private. Infrastructure leaves `private-docs`, documentation
stays (§6.1). 5 A: the `creche` family may open PRs in `creche-release`,
and every change reaches the host only through a tapped `host` release. So
the site ships in the `host` release, and decision 3 becomes "with the tap".
This needs `github_token_platform` and the platform fence to gain
`creche-release` (a registry family-file PR and a GitHub token change by
The operator).

The operator's answers on stage 2, 2026-10-31:

6. `host` is a new kind, `units`: no build, root copies the fetched tree,
   step 9 installs the unit files.
7. Root installs each unit file as a symlink into `/opt/components/host`.
   The tree swap changes every unit at once, and a restore is the swap back.
8. A unit file deleted from `creche-release` is stopped, disabled and
   unlinked by the next `host` release, for a link into the `host` tree only.
9. "Basically nothing should require sudo." Every step of a `host` release
   runs in root's step 9, after the tap. The one sudo step left is removing
   the `creche-deploy` sudoers entry, once, at the end of stage 3.

## 10. The site moves into the `host` release

Date: 2026-11-03. Status: **proposal, open questions in §10.6.** Decision 5
(§8) says the site ships in the `host` release, with the tap. This section
says how.

### 10.1 What reads the two files today

Read from `origin/main` of creche, chaperone, creche-release and private-docs
(private-docs `a2c9baf`). Not yet checked on the host.

| Link | Target today | Who reads it |
|---|---|---|
| `/etc/creche/site.env` | `/opt/private-docs/site.env` | every component unit (`EnvironmentFile=`), the follower, root's executor and the requester (`handover/site.py`), the watchdog, the drift check, `fleet-up`, `provision-library.sh` |
| `/etc/creche/secrets.enc.env` | `/opt/private-docs/infra/secrets.enc.env` | the handover wrapper (`RELEASE_GITHUB_TOKEN`, `RELEASE_APPROVAL_URL`, `RELEASE_APPROVAL_TOKEN`), and `fleet-up` (`LITELLM_MASTER_KEY`) |

Three facts shape the design:

1. **The secrets file has a third reader, not through the link.**
   `ai-stack.service` runs `sops exec-env secrets.enc.env` in
   `/opt/private-docs/infra`. The compose plane uses the other 20 keys.
2. **The secrets file holds the tap's own keys.** `RELEASE_APPROVAL_URL` and
   `RELEASE_APPROVAL_TOKEN` say where root asks for a tap.
3. **`/opt/private-docs` has other readers.** `ai-stack` (`infra/`), and the
   personal units `docs-mirror`, `ocr-watcher`, `nodered-flows-sync` and
   `restic-backup` run from it. So `/opt/private-docs` cannot go yet.

Root's checks already fit a target inside `/opt/components/host`:
`handover/site.py` needs a root-owned file with no group or other write bit,
and the wrapper's `require_root_chain` needs root-owned directories up to `/`.
Step 8 copies the tree as root with `copy2`, so each file is root-owned with
git's mode.

### 10.2 What moves into creche-release

| File in creche-release | From private-docs | Note |
|---|---|---|
| `site/site.env` | `site.env` | byte-equal copy. S4 changes the header comment to name the new link target, after the re-point |
| `site/secrets.enc.env` | `infra/secrets.enc.env` | byte-equal ciphertext. sops's MAC covers the values, not the path, so the file decrypts as before |
| `.sops.yaml` | the `infra/secrets\.enc\.env$` rule only | its `path_regex` becomes `site/secrets\.enc\.env$`, so `sops` on the Mac finds the recipients |

The gate gains four rules (`bin/check-tree` and `gate.yml`):

1. `site/` holds exactly those two files, each a regular file, never a link.
2. `site/site.env` passes creche-env's checker (`creche-env check --env`),
   from the creche commit `uv.lock` already pins. Not yet checked: its trust
   check may refuse a file the CI runner owns. S1 finds out.
3. `site/secrets.enc.env` is a sops file: each value is `ENC[...]` and the
   `sops_mac` line is present. A plaintext secret never lands.
4. A change to `site/secrets.enc.env` fails the gate unless the operator opened the
   PR. §10.6 Q1 says why.

### 10.3 The one root step

Done once by the operator, after a `host` release with `site/` is live.

1. Read-only check first: each new file is byte-equal to the file the link
   names today.

   ```bash
   cmp /opt/components/host/site/site.env "$(readlink -f /etc/creche/site.env)"
   cmp /opt/components/host/site/secrets.enc.env "$(readlink -f /etc/creche/secrets.enc.env)"
   ```

2. Re-point both links. `mv -T` replaces each link in one rename, so no
   reader sees a missing file.

   ```bash
   sudo sh -c 'ln -s /opt/components/host/site/site.env /etc/creche/site.env.new && mv -T /etc/creche/site.env.new /etc/creche/site.env'
   sudo sh -c 'ln -s /opt/components/host/site/secrets.enc.env /etc/creche/secrets.enc.env.new && mv -T /etc/creche/secrets.enc.env.new /etc/creche/secrets.enc.env'
   ```

No unit restarts: the bytes are the same. The rollback is the same two
commands with the old targets. A `host` release later swaps the tree under
the link, so the link never changes again.
