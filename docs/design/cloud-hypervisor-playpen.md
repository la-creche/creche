> Status as of 2026-11-14: Done. The Cloud Hypervisor playpen is live and the sbx playpen is retired (phase 11, 2026-11-13). The text below keeps the sbx comparison as the record of why the move was made.

Brief: [cloud-hypervisor-agent-prompt.md](cloud-hypervisor-agent-prompt.md). Research date: 2026-11-01. Sources: creche, registry, chaperone, mcp and private-docs at origin/main, plus read-only checks on the host.

## 1. Goals

1. Startup speed and turn speed rank first. Today every sbx call costs about 4 s.
2. Replace sbx with Cloud Hypervisor (CH). Decided by the operator on 2026-11-02.
3. Meet the operator's four access goals:
   1. All agents can use the shared memories and information in Obsidian.
   2. `code` works on any repo shared through the code token, and on any repo the operator asks for.
   3. `creche` holds the platform token and works on anything la-creche related.
   4. Every coding agent has its tools and folders. Its work is saved, so the same agent keeps what it worked on.
4. Nothing needs sudo, except steps this note names one by one.
5. Type-driven design: parse at each boundary, newtypes for ids and paths, enums over strings, one wire definition per type.

| CH19 | What stops the facade | The vmm owns the stop. Amends CH5d, CH7-6 and CH8-2. (1) Guest init keeps the facade for the VM life. A vsock link close never stops it, so a restore keeps the facade (fact 45). If the facade exits, guest init starts a new one only after `waitpid` reports the old one gone, so at most one runs. (2) A new control link on 1200 replaces the old one. The handshake reports facade state, pid, start count and whether a turn is running. (3) A graceful stop: the vmm sends `stop` on the control link. Guest init stops the facade (up to 30 s with a turn running), syncs and powers off. SIGTERM, then SIGKILL, is only the fallback, because a kill is a power cut for the guest. (4) CH dies with the vmm: the vmm sets `PR_SET_PDEATHSIG` before it starts `systemd-run`, from a long-lived thread. Not `BindsTo=vmm.service`, which would stop every VM before the vmm can snapshot it on a restart. At start, the vmm kills every leftover per-VM scope (never adopts) before it binds or unlinks any per-VM socket path. It unlinks a stale CH vsock socket before boot or restore. (5) A snapshot is single-use: the vmm marks it consumed at resume. After any stop without a fresh snapshot, the next start is a cold boot. (6) The vmm snapshots a VM only when the facade is up, no turn is running and no door link is open. To evict a VM with a door link open, it closes the door link first, and the client reconnects with `session/load`. The session disk OFD lock (CH v54, always on) stops a second CH on one session disk. Attendance drops `wait_out_lock` and `OrphanFacade`. The facade in CH mode drops the lock and the beat deadline. Rejected: a re-open timer in guest init, a kernel-log restore check (printk text is not a stable interface, and Linux exposes no VMGENID change to userspace), and a facade restart after each restore (defeats CH2). ## 3. Architecture

### 3.1 What runs today (facts that change the brief)

1. **sbx already boots a VM per use.** Only one sbx VM runs now (`coding-sandbox-s19`). The others stop when idle (`auto-stopped runtime after last session disconnected`). Every `status.json` still says `power=running`.
2. **One family = one facade = one `flue.db` = one workspace.** All sessions of a family share one Node process, one SQLite file and one tool folder (`/srv/agents/sessions/<family>/workspace`), as root. Any door client of a family can load or prompt any session of that family. Decisions D0.5 and D2.1 fix this model.
3. **ACP session id = Flue instance id = `creche_sessions.id`.** The facade mints it inside the VM (`randomUUID`). The door and attendance never read it. Panda sends `session/new` on every fresh page connect.
4. **Panda already has delete, resume and close.** Upstream Panda (`<panda-checkout>`) sends `session/delete` from a sidebar button. A graceful exit (`shutdown-vmm`, guest poweroff, SIGTERM) removes both sockets. Under Landlock CH cannot unlink `api.sock.lock`, so the vmm removes it. Correction 2026-11-04: on CH v54 a stale `api.sock` does block a start under Landlock, because CH removes it itself before it binds and the ruleset grants no remove right. The vmm removes it first (PR #458).
76. **`PR_SET_PDEATHSIG` through `systemd-run --user --scope` works** (spike 2026-11-03, systemd 255.4). Set in a pre-exec step, it survives both execs. On `kill -9` of the parent the child dies in 1.2–2 ms (`sleep`) or 20–30 ms (CH booting), and the scope is gone with no further step. A `systemctl --user stop` of the parent's own scope kills CH in 33 ms. A child forked from a thread that later exits dies when that thread exits (4 of 4), so the spawn needs a dedicated long-lived thread. Leftover scopes are found by name prefix (`list-units 'prefix-*'`, 9 ms) and stopped with `systemctl --user stop` (64 ms for CH). `systemd-run --unit` with the name of a live leftover fails.
77. **One Landlock ruleset covers boot, snapshot and restore** (spike 2026-11-03, kernel 6.8.0-142, Landlock ABI 4). Applied before exec, it handles all ABI-4 file rights plus TCP bind and connect with no port allowed. Smallest set: CH binary (execute, read), `/dev/kvm` (read, write), `/dev/urandom` (read), kernel (read, boot only), root disk (read only, so CH8-8 holds), session disk (read, write), run folder (make socket, make file, write, truncate), snapshot folder (make file, write, read). Applied before `systemd-run`, it also needs `/usr/bin/systemd-run` and the dynamic loader (execute, read) and `/usr/lib/x86_64-linux-gnu` (read). A restored CH's API thread is confined: a snapshot to a forbidden folder fails EACCES, and TCP connect is refused. Boot, snapshot and restore times are within noise of no Landlock. Landlock ABI 4 does not cover UDP or AF_UNIX (a connect to `/run/user/1000/bus` succeeded), so the CH8-1 AppArmor profile is still needed. CH still rejects `--landlock` with `--restore` (fact 64).
78. **CH v54.0 builds static for x86_64 musl in CI with the CH7-4 argv** (spike #386, 2026-11-04, ubuntu-24.04, Rust 1.92.0). `cargo install --locked --no-track --git … --rev 038ce5a72d761380a02f714a4eb4ca63e0ea073d cloud-hypervisor --bin cloud-hypervisor --bin ch-remote --target x86_64-unknown-linux-musl` finished in 5 min 34 s. Both programs are `static-pie linked` and stripped, and print `v54.0.0` (the crate version, because a `--rev` fetch brings no tag for `git describe`). sha256 `cloud-hypervisor` `418cd9b3…4b4e`, `ch-remote` `ac3edcfe…89a2`. ### 3.2 Target design

One Rust program, the vmm, owns every VM on the host. Each session gets its own Cloud Hypervisor VM, and the VM reaches the host only over vsock. This section restates sections 2 and 3.1 as one picture. It adds no decision.

```
HOST (the host)                     |  VM (one per session)
                                    |
caregiver, attendance --client--> vmm
attendance --ACP (path open)--------|--> facade
vmm ================================|==> guest init (PID 1)
LiteLLM 192.0.2.10:4000 <--- vmm <===|=== 127.0.0.1:4000
chaperone 192.0.2.10:8300 <- vmm <===|=== 127.0.0.1:8300
creds.json, config/ ---> vmm =======|==> family-state reply
code mirror -----------> vmm =======|==> git clone (repos list)
internet :443 <---- vmm proxy <=====|=== egress (non-empty egress list, today code and creche)

=== vsock, one fixed port each. No network card.
```

#### 3.2.1 Components and who runs them

The VM runtime:

| Part | Language | Runs as | Job |
| ---- | -------- | ------- | --- |
| vmm | Rust | <user>, user unit (fact 57) | Owns CH processes, session disks, snapshots, the egress proxy, live creds and config, and the session list (CH9). Serves HTTP on `/run/user/<uid>/vmm/vmm.sock` (CH20). Installed root-owned at `/opt/components/vmm` (CH7-5). |
| cloud-hypervisor | Rust (upstream) | <user>, one `systemd-run --user --scope` per VM | One process per VM, a child of the vmm (CH8-2). Built and signed in CI (CH7-4). Confined as in 3.2.5. |
| guest init | Rust | PID 1 in the VM | Bridges guest ports to vsock (CH6-2). Parses `/etc/creche/env` (CH7-7). Runs one facade for the VM life and restarts it after a crash. Stops it and powers off on the vmm's `stop` (CH5d, CH19). |
| facade and agent | TypeScript (Flue) | in the VM | One facade per VM (CH1, D2.1). Pulls family state before each prompt (CH5a). |

Clients and services on the host:

| Part | Runs as | Job under CH |
| ---- | ------- | ------------ |
| caregiver | <user>, user unit (Python) | Only writer of `creds.json`, `config/` and the per-family egress allowlist (CH5b, CH6-4). A client of the vmm over `vmm.sock` (CH9, CH20). |
| attendance | <user>, user unit (Python) | Door and job queue. Routes each request by session id (CH1). A client of the vmm over `vmm.sock`, with one HTTP Upgrade connection per ACP stream (CH9, CH20). |
| chaperone | `chaperone` | Holds every credential. A VM reaches it only through the 8300 plane. |
| `mcp-memory` | `mcp-memory` | Chaperone upstream for every vault read and write (CH4a, CH4d). Its design waits on the deferred research (section 4, item 11). |
| code mirror | <user> | `/srv/agents/code`, also the release source (fact 13). Only the vmm serves it to VMs (CH3). |

Later, a chaperone `git-platform` upstream (user `mcp-git-platform`) fetches and pushes for `creche` only (CH3). Wire types are defined once in Rust. The Python types are generated from them (CH9).

#### 3.2.2 The life of a session

Open:

1. `session/new`: The host answers, and no VM starts. The vmm adds the session to its session list (CH1).

Boot, at a prompt that finds no running VM:

1. The vmm runs admission (3.2.5).
2. The vmm applies its Landlock ruleset and starts CH in its scope (CH8-2, CH8-3).
3. If a memory snapshot exists and its keys match, the vmm restores it (about 50 ms, CH2).
4. Otherwise the vmm cold-boots from the session disk (CH2). The cold boot takes about 0.3 s plus the facade start. The facade start is not measured (item 2).
5. Each VM start, cold boot or restore, names the initramfs that the vmm wrote once at its own start (CH62 rule 18, CH61 rule 3). The vmm passes the session identity in the guest init handshake (CH5e).

While it runs:

1. Before each prompt, the facade pulls the family-state reply. It sends no revision, and the vmm sends the full typed state on every pull (CH23, amending CH5a).
2. A changed `model.router` takes effect at the next prompt (CH5c-2, item 5.3).
3. Turns reach LiteLLM and the chaperone through guest init's local ports 4000 and 8300 (CH6-2).

Idle and resume:

1. An idle VM saves a memory snapshot, and its CH process stops (CH2). The idle timeout is a value to measure (CH2). Under RAM pressure, admission snapshots the least recently used idle VM sooner (CH8-6).
2. The host drops a snapshot after 7 days (first value, CH2). It drops snapshots sooner, oldest first, past about 150 GiB (CH8-7). The session disk stays until a delete: a client `session/delete` (CH27), a job end (CH21-2) or a family delete (CH21-10).
3. A snapshot is keyed on the CH rev, kernel digest, root disk digest, initramfs digest and guest-init protocol version (CH7-6, CH61 rule 3, CH62 rule 24). On a mismatch the vmm drops the snapshot and cold-boots from the session disk (CH7-6).
4. A restore resets every vsock connection, so the guest bridge reconnects (fact 45). The facade keeps running (CH19).
5. The vmm snapshots only when the facade is up, no turn is running and no door link is open. A snapshot is single-use: after a resume, the next start without a fresh snapshot is a cold boot (CH19).

Thin jobs (coding-sandbox) get one VM per job, and the vmm drops it at job end (CH1). A job keeps no snapshot (fact 62). The vault-oracle family goes away (CH4d).

#### 3.2.3 The vsock port map

The vmm listens on these fixed host-side vsock ports for each VM, and binds 1103 and 1104 only where the row says so (CH49 rule 3, CH69 rule 13). It checks this at create and after each egress edit (CH6-3). The port numbers are CH14.

| Port | Direction | What the vmm does |
| ---- | --------- | ----------------- |
| 1100 family state | guest → host | Answers with creds and config read from caregiver's files (CH5a, CH5b). |
| 1101 LiteLLM plane | guest → host | Splices bytes to `192.0.2.10:4000`. No allowlist lookup, no rewrite (CH6-2). |
| 1102 chaperone plane | guest → host | Splices bytes to `192.0.2.10:8300` the same way (CH6-2). |
| 1103 git mirror | guest → host | Serves a clone only if the repo is in the family's `repos` list and in the mirror (CH3, CH10-10). The vmm binds it only for a family with a non-empty `repos` list (amended by CH69 rule 13). |
| 1104 egress | guest → host | HTTPS-only allowlist proxy. Only a family with a non-empty egress list gets this port, today code and creche (CH6-1, CH8-1, amended by CH49 rule 3). |

The ACP link and the guest init handshake go the other way (CH13). Guest init listens on vsock. The vmm reaches it by sending `CONNECT <port>` on the VM's CH socket: once for the control link, and once per door connection for ACP. These guest-side ports reach nothing on the host: 1200 for the control link and 1201 for ACP (CH14). Later, `creche` gets one more port for the `git-platform` bundle spool (CH3).

Nothing else reaches the host. Agents are air-gapped from the host (CH8-1).

#### 3.2.4 Disks and images

1. Root disk: one shared read-only ext4 per flavor: base, python and coding. The coding flavor serves code and creche (CH7-1).
2. CI builds each root disk from `playpen/Dockerfile` with `buildx --output type=tar` and `mke2fs -d -`. CI compresses it with zstd and signs it with cosign. Root checks the signature and installs it after the tap. The host builds nothing (CH7-2).
3. Guest kernel: the CH prebuilt `vmlinux-x86_64`, pinned by digest and shipped like the disks (CH7-3).
4. Initramfs: the vmm writes it at VM start. It holds guest init from the same release (CH7-6).
5. Session disk: one 16 GiB sparse disk per session, holding `flue.db` and the workspace (CH2, CH8-7). Per-session disks replace D0.5 (CH1).

The vmm copies root disks into its own digest-named store, because a release renames old trees (fact 56). The kernel probably needs the same store for the same reason (inference). The vmm checks the root disk digest at VM start (CH8-8).

#### 3.2.5 Confinement and limits

Layers around each CH process (CH8-1):

1. CH seccomp, on by upstream default. Each CH rev bump must pass a CI smoke test (CH8-4).
2. One Landlock ruleset per VM. The vmm applies it before it starts CH, on boot and on restore (CH8-3). It gives CH read-only access to the root disk and denies TCP (CH8-1, CH8-8). A spike comes first. If the spike fails, the fallback is CH's `--landlock` on boot only, until CH issue #9118 is fixed.
3. One AppArmor profile for `/opt/components/vmm/bin/cloud-hypervisor`. It denies every Unix socket except the VM's own vsock and API sockets. It needs one sudo install now. It needs a sudo reload each time its rules or the install path change (section 6).

Limits:

1. Per-VM scope (CH8-2, CH8-5): `--cpus boot=N` and `CPUQuota` = N × 100%, from family `cpus`. Guest RAM comes from family `memory`, and `MemoryMax` = guest RAM + 512 MiB (to measure). `TasksMax=256`. A balloon with free page reporting and deflate on OOM. No core dumps.
2. Admission: the configured guest RAM of running VMs stays at or below 80 GiB. Past that cap, the vmm snapshots the least recently used idle VM. With no VM idle, attended sessions get `host_full` and jobs queue. This replaces `max_resident_processes` (CH8-6).
3. Disk: a rate limiter with `refill_time` ≥ 1000 ms, and a free-space floor in admission (CH8-7).

Risk: a wrong AppArmor rule after a CH upgrade stops VMs from starting until the operator reloads the profile (CH8-1).

## 5. PR sequence

## 6. Host steps for the operator

Agents never run these steps. Each step names whether it needs sudo and why, and gives a command where one is known. The "needs sudo" group lists every root step this design adds (goal 4). Placeholders in `<>` are values that are still open.
